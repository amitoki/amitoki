# stegrdbの監査・検証記録

基準は`main`の`30131e9`。`feat/relay-plugins`で中継APIとPostgreSQLを分離し、送受信の欠損につながる処理を修正した。従来版はビルドできたが、自動テストがなく、11件のコンパイラ警告があった。

新しい実装では、通常のテスト22件、PostgreSQL試験3件、隔離ネットワーク試験1件を確認した。さらに3台のVMで実通信とノード停止後の再配送を確認した。大規模な長時間運用や物理NICの特性までは検証していない。

## 欠損・異常終了につながる処理を修正した

| 基準版の問題 | 対応 | 検証 |
| --- | --- | --- |
| DB取得時に送信前のパケットを処理済みにする。送信失敗後も受信位置が進む | NICへの送信に成功した分だけACKする | 2個目の送信を失敗させ、残りがキューに残ることを確認 |
| `timestamp > last_timestamp`とLIMITの組み合わせで同時刻のデータを取りこぼす | ノードごとの未処理キューを読む | 同時刻2,048件の分割取得と、後からコミットされたデータを確認 |
| DB書き込み失敗時にdrain済みバッファを失う | 同じUUIDとバッファで再試行する | DB受け付け直後の通信断を模擬し、二重保存されないことを確認 |
| TCP固定の解析でUDPを誤解釈し、短いTCPデータで範囲外アクセスする | IP長・TCP長・UDP長をそれぞれ検証する | 8バイトUDP、短いTCP、不正IHL、任意の短い入力を確認 |
| IPフラグメントに対し通常のL4ヘッダとしてポートを読む | 再構成していないフラグメントは明示的に拒否する | IPv4/IPv6のフラグメント拒否を確認 |
| 1500バイト制限がEthernetヘッダ込みの正常な1514バイトを落とす | フレーム長とIPのMTUを混同しない | 仮想NICを通して1514バイトの送受信を確認 |
| 受信EAGAIN後に待機せずループし続ける | `AsyncFd`で読み取り可能になるまで待つ | 単一スレッドで3ノードを動かし、アイドル中のタイマ進行を確認 |
| 同じfdをpnetとOwnedFdの両方が所有する | ソケットの所有者を一つにする | pnetへのfd引き渡しを廃止し、raw socket実装を独立させた |
| 無制限のグローバルバッファと、実際には送られない停止通知 | 上限付きキュー、キャンセル、残りの送信、停止期限を実装 | 中継先停止時の上限と、停止時のバッファ送信を確認 |
| 初期化SQLの文字列破損と末尾カンマ | 旧SQLを修正し、新実装は専用スキーマへ分離 | 旧SQLの構文エラーを再現し、修正後の実行成功を確認。新スキーマも試験で作成 |

初回に見つけた旧リポジトリ参照の`setup.sh`も変更した。現在はローカル設定の準備とビルドを行い、ディレクトリの削除や別リポジトリのcloneは行わない。

## DB以外の中継方式を追加できるようにした

SQL、接続管理、DB型が、パケット解析・フィルタ・起動処理へ広がっていた。これらを`plugins/postgres`へ移し、コアは`Relay`の送信・受信・ACKだけを呼ぶようにした。設定とフィルタもTOMLへ移したため、非DBプラグインにPostgreSQLへの接続を要求しない。

`--no-default-features`でPostgreSQLを除いたビルドとテストを行った。メモリ中継を参照実装として用意し、具体的なDB型を共通APIへ戻さなくても、同じエンジンを動かせることを確認した。

PostgreSQLのノードIDは専用接続のadvisory lockで占有する。接続が切れた場合は停止し、再起動時にキューを引き継ぐ。これはネットワーク分断をまたいだ完全なfencingを保証するものではない。障害を検出する前に進行中だったNIC送信は取り消せない。

## 待機・コピー・DB往復を減らした

フレーム本体を`Bytes`で共有し、再試行時に全フレームを複製する処理をなくした。受信用バッファも使い回す。書き込みは規定で128件ずつ、または10ミリ秒でまとめる。空のバッファを定期的にdrainする処理はなく、データ到着から待機を始める。

PostgreSQLの接続とprepared statementを接続単位で再利用する。以前のstatementキャッシュは参照するだけで登録されていなかった。NICの送信用ソケットも起動時に一度作り、バッチごとの再作成をやめた。フレームごとのINFOログと、解析途中の同期ファイルflushも送受信経路から外した。

ローカル測定の参考値は次のとおり。旧版との同条件比較ではなく、実装後の動作確認用の値である。

| 対象・条件 | 結果 |
| --- | --- |
| 1514バイトUDPの解析＋空blacklist評価。releaseビルド、100万回 | 約29.6ns/フレーム |
| PostgreSQL 17、localhost、1024バイト×2,048件、128件/バッチ。debugビルド | 保存約276ms |
| 同データの保存、2受信ノードで全件取得、各バッチでACKを二度実行する冪等性試験 | 約482ms |

DB測定には通常のSQL往復とテストの検証処理を含む。別の並行テストも動いている。ネットワークを越えたトンネルの帯域・遅延を示す値ではない。規定の空キュー確認は10ミリ秒ごとなので、受信側1ノードあたり最大約100回/秒の問い合わせが発生する。

再現には`cargo bench --bench packet_pipeline`と`bash scripts/test-postgres.sh`を使う。OSはUbuntu 26.04、Rustは1.98.1。ネットワーク試験はUbuntu 24.04コンテナ内の3組のvethで、外部接続を無効にして実行した。

## 3台のVMをまたぐ通信を確認した

QEMU 10.2.1/KVMでUbuntu 24.04のVMを3台作り、各VMにreleaseビルドのstegrdbを配備した。DBはVM a内のPostgreSQL 16。中継対象LANは各VM内のvethとnetwork namespaceで、VM間の直接接続はない。

a→b、b→c、c→aで、それぞれICMPを3回、TCPを2MiB、1472バイトのUDPを64件送った。ICMPはフラグメント禁止で全件到達し、TCPとUDPは内容が一致した。VM cの中継サービスを停止している間に送ったUDP 64件はDBへ蓄積され、再起動後に全件が届き、ACKによって未処理キューから消えた。

VM全体を停止・起動し直し、同じ試験の成功も確認した。3台ともホストの最新releaseバイナリとSHA256が一致している。

手順と構成は[VMラボ](vm-lab.md)にまとめた。初回の結果は`artifacts/vm/2026-09-26/164815/result.json`、再起動後は`artifacts/vm/2026-09-26/165127/result.json`。各ディレクトリにjournalも保存している。この試験は少量の通信による機能確認であり、最大帯域や負荷時の損失率の測定ではない。

## 実運用前に確認する点

NICへの注入直後にプロセスが落ちた場合の再送は残る。送信成功とDBのACKを原子的に確定できないため、配送はat-least-onceとなる。強制終了時のメモリ上の未保存データや、負荷が受信能力を超えたときのカーネル側のパケット損失も保証対象外。

DBの自動削除・保存上限は未実装。保持期間と廃止ノードの整理は運用側で決める必要がある。同一channelの送信を直列化しているので、多数の送信元がある負荷は別途測定する。物理NICのVLANオフロード、チェックサムオフロード、ジャンボフレーム、複数ノードが同じL2へ接続される構成は未検証。IPフラグメントは拒否し、再構成機能は持たない。

次に性能を詰める際は、想定するパケットサイズ・毎秒件数・ノード数・許容遅延を決め、遅いDBやノードの再起動を含む長時間試験で測定する。今回のプラグイン分離により、その結果に応じて通知型DB受信や別の中継方式へ差し替えられる。
